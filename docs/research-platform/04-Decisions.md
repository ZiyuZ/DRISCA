# 关键约定与待讨论事项

## 已确定的方向

Launcher 管理一组实验所用的 Unreal 进程，启动一次 Unreal 后可以连续开始和结束多次实验。主机配置分别保存 UE 编辑器版和打包版运行路径，界面与命令行共享同一套管理服务操作。

CARLA 继续提供地图、物理、车辆动画、渲染与可复用的仿真能力。DRISCA 建立专用 JSON 接口和 Python 客户端，逐步覆盖当前使用的官方客户端功能。

先完成单机原生驾驶，再完成中心服务和双终端交互，之后增加交通行为模型。终端之间通过中心服务交换车辆状态。

Unreal 负责本地画面、键盘和连续控制。Python 负责实验逻辑与数据处理，现有 Web Launcher 保留。方向盘按当前设备单独接入。

主视图与三路独立后视镜按 60 FPS 目标实施。开发机使用适合屏幕的窗口，5760×1080 留到三屏实验机检查。相机安装继续使用包围盒比例坐标，窗口与镜面屏幕布局仍属主机配置。

当前驾驶通道采用 worker 连接本机 Unreal 的 TCP JSON 请求响应，状态由 Unreal 在物理更新结束后汇总为最新快照。控制连接持有活动驾驶视图，意外断开后停止视图并恢复默认视角，实验通过 Python 的失败收尾路径结束。多人阶段由终端 worker 连接中心服务，本机驾驶通道保持现有方向。

## 实施时保持的细节

每辆车保持一个明确的运动计算来源。人工、模型和远端状态接入时，通过控制来源切换协调车辆运动。

驾驶人输入与车辆实际控制分别记录，自动驾驶期间保留驾驶人操作。连续状态采用最新快照，实际采样间隔由数据中的帧号和时间反映；离散事件保持自己的记录路径。

键盘反斜杠表示驾驶人主动切回人工驾驶，执行模式切换并记录事件。Launcher 的“请求接管”表示操作者要求驾驶人接管，按指令配置播放语音。语音由 Launcher 负责，后续独立语音服务也由 Launcher 侧管理。

状态中的运动数据具有明确的采样时刻。各终端时间与帧号分别保存，中心接收时间独立记录。中心呈现的全局视图用于协调，分析使用原始来源信息。

位置、速度、角度和车辆身份在接口中保持统一含义。内部速度沿用 m/s，界面按需显示 km/h。地图、坐标原点与车型资源在参与同一实验的终端之间保持一致。

原生显示与数据保存分别处理。远端车辆平滑显示使用接收状态，研究记录保留原始来源数据。物理执行和轨迹播放的来源在数据中可识别。

原生改动集中在新增的专用实现中，复用 CARLA 现有能力。类、线程和协议只处理当前功能所需的问题，错误直接报告。构建前确认现有构建任务，按仓库说明执行。

## 近期需要对齐

### 通信传输

业务消息统一使用 JSON。单机驾驶通道继续使用已经实现的 TCP JSON；专用接口完整替换官方客户端时，结合实际接口范围评估传输方式。终端到中心的通信在多人阶段确定，Python 对外的方法保持直接。

选择依据是原生端接入量、现有库、消息边界处理和调试便利性。图像留在本地 GPU，当前传输承载命令、状态和事件。

连接方向、请求或推送、断线后的处理分别按具体链路决定。当前控制连接断开按实验失败处理，重新开始实验时建立新的控制连接。

### 当前阶段的工作范围

正在进行的原生驾驶实现以单机可用为交付。专用接口完整替换官方客户端安排在第二阶段。交接时需要明确这两个阶段的边界，保持已完成工作与后续迁移相互衔接。

## 到对应阶段再确定

多人实验开始前，确定首批交互场景和主要研究指标，据此选择可接受的延迟与时间对齐方式。实际运行记录用于判断是否需要进一步提高同步精度。

交通模型接入时，选择第一个真实研究场景，例如固定路线跟驰。围绕它确定模型输出目标加速度、目标速度、轨迹还是底层控制，再增加对应执行能力。

若研究涉及车辆接触与碰撞结果，确定碰撞判定来源以及终端间的处理方式。首批多人场景可以先围绕正常驾驶交互开展。

外部交通仿真接入时，决定优先保持外部轨迹还是采用 CARLA 物理追踪。这一选择影响轨迹误差、车辆动力学与结果解释，车轮动画分别按所选执行方式完善。
