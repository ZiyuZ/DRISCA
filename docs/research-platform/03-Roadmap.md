# 实施阶段

每阶段完成一个可以实际使用的结果，先运行最直接的流程，再处理发现的问题。具体类结构与文件划分由已有代码和当前需求决定。

## 第一阶段 单机原生驾驶

目标是通过 Launcher 完成一次原生驾驶实验。

Unreal 承担主视图、三路后视镜、键盘和连续控制。Python 通过独立接口启动和调整驾驶视图、读取最新状态，继续管理尚由官方客户端承担的场景与采样功能。先接通主视图和开始结束，再加入镜面与配置调整。

Launcher 使用主机配置管理 CARLA 启动与窗口尺寸、位置和边框样式。单次停止实验后保留 CARLA 进程，恢复默认视角。驾驶状态按实际采样时间与帧号保存。

开发机用适合屏幕的分辨率检查驾驶响应、焦点变化、相机调整、保存数据、连续开始结束和地图切换。三屏实验机验证 5760×1080 的实际表现。方向盘后续作为一项明确设备功能接入，沿用当前设备约定。

完成条件：现有 Launcher 能启动一次实验、正常驾驶、调整画面、结束并查看数据；原生显示与输入链路有实际运行记录。

### 当前进展与下一步

2026 年 11 月 22 日在开发机通过 Launcher HTTP/CLI 完成单机联调。窗口为 1600×900，使用 UE 编辑器版运行，同一 Unreal 连续完成保存数据和关闭保存的两次实验，停止后均释放实验车辆并恢复默认自由视角。

运行期相机、后视镜布局和天气调整已生效。保存实验的帧号唯一，自动驾驶模式与实际控制量进入数据库；关闭保存的实验保持完整运行流程。视图异常停止后 worker 抛错退出，会话记为 `aborted`，随后可以重新开始实验。关闭 Launcher 的共用停机路径已验证先收尾实验、再回收 Unreal。

同日完成用户实际键盘驾驶联调，验证人工输入、车辆实际控制、自动驾驶切换与主动接管、碰撞与压线事件、操作者打点、备注、连续实验及 CSV 导出。主会话保存 9100 行数据，对应 9100 个不同世界帧；关闭 Unreal 导致的会话异常结束也已验证。按键接管只切换人工模式，Launcher 请求接管指令播放所配语音。

打包版启动、三屏 5760×1080 和实验机窗口位置继续安排实机验证。方向盘整体等待硬件到位后接入，现有设备封装保留。第二阶段专用接口替换已完成接入，迁移后的验证见下文。

## 第二阶段 专用接口替换官方客户端

目标是让 DRISCA Python 代码通过自己的接口完成现有单机功能。

先梳理实际使用的 CARLA 类型与方法，将其对应到原生端操作和普通数据。逐项接入地图、车辆、天气、道路信息、传感器事件和录像等能力，复用已有底层实现。

Python 保留编排与存储，原先依赖 carla 对象的状态计算改用自有数据。接口同时提供实验操作和逐车状态、控制能力。一次请求可携带多辆车的数据，按实际使用需要组织。

迁移过程中验证每项功能的数据含义，重点包括压线、车道偏移、速度单位与录像。自动驾驶控制来源接入按已选模型处理，既有功能在替换过程中明确对应关系。

完成条件：单机实验通过专用接口完成，Python 运行依赖中移除官方 carla 包，现有界面操作与数据字段有对应实现。

### 专用接口当前进展

2026 年 11 月 23 日，原生 WebSocket API 完成编辑器构建、地图与天气、全车快照、研究采样、逐车控制权、道路图、信号关联以及录像正常/异常收尾的运行验证。Python 已移除 carla wheel，完成客户端与 worker 接入。Launcher 在 Town10HD_Opt 完成保存与关闭保存、连续实验、运行期调整、事件关联、录像信息、导出与异常退出验证；连续切图、仿真时钟及传感器同帧同时间已核对。通信调度优化后，原生定点测得 exchange 中位约 52 毫秒。

当前收尾界面调整并排查 Singapore_Intersection 车辆生成失败。随后扩展全局雾与局部团雾，支持 Python 配置与动态调整，再校准能见距离。打包版、三屏和方向盘继续按设备与交付安排验证。

官方 Traffic Manager 宿主方案取消。后续先在 src/drisca/traffic/ 实现自研 Python 交通模块，从路线跟踪与速度控制推进到跟驰、随机选路、换道和路口规则，再开展中心服务与双终端。当前人工驾驶流程继续验证，自动驾驶启用明确报错。

## 第三阶段 中心服务与双终端驾驶

目标是两台驾驶终端通过中心服务参加同一次实验，彼此看到对方车辆。

先建立中心服务的实验管理、车辆身份、控制来源、状态接收与转发能力。每台终端负责本车输入和运动，接收其他车辆状态并更新副本。共享地图和环境由中心协调。

中心先完成车辆状态协调与集中记录，随后加入终端启动、实验开始结束等操作者流程。远端车辆显示保留滚动、转向和车灯表现，观察更新延迟与运动连续性。

记录各终端原始时间和帧号，并记录中心接收时间。检查两名驾驶者的跟驰、会车和换道互动，再扩展到第三名驾驶者。

完成条件：中心组织一次双终端实验，驾驶端本车操作直接、远端车辆可见且运动连贯，数据可以按来源还原各车运动和输入。

## 第四阶段 自定义交通行为与混合交通

目标是在多人或单人实验中加入研究人员控制的交通车辆。

先实现一辆模型车辆沿指定路线行驶，提供必要的目标速度或底层控制能力。再接入简单跟驰与换道模型，按车辆指定控制来源。交通模型运行在中心机器的 Python 环境，原生端执行运动与呈现。

研究脚本可以读取所需车辆、车道和交通信号信息，计算并提交控制。根据实验逐项增加汇入、让行、切入等动作。交通模型扩展以实际实验代码为依据。

外部轨迹与 SUMO 等工具按具体研究需要接入，明确使用轨迹播放还是物理追踪，并检查车辆动画和数据含义。

完成条件：人工与模型车辆共同参与实验，研究人员能够替换或修改一个行为模型，并观察到对应车辆和交通交互的变化。

## 发布收尾

各阶段稳定后整理运行程序、私有 Python 环境、配置和资源，形成可直接启动的发行目录。完整发布重点检查另一台机器上的启动、资源路径与实验脚本使用方式。

构建与打包采用两个仓库已有流程。一次性操作与原始结果留在 .local/，操作人员文档围绕安装、启动、实验与数据使用维护。
